# Changelog

One entry per release, newest first. Releases are published from the Desktop workflow; the installer and update files are on the GitHub release page. Entries before 30.3.0 are written from the commit history, and describe what was built; some of it was first tried on a real PC only afterwards.

## Unreleased

- **Counts no longer have crooked digits.** The rolling number in "831 videos · 1 channel", "314 performers" and the other counts placed each digit by a pixel measure that was rounded to a whole pixel, so digits such as 7 and 9 sat up to 3 px too high next to the words around them. The digits are now placed in the same unit as the text.

- **A page file that cannot be fetched no longer ends in an error screen.** If the app was updated or restarted while a tab was open, opening a page (Operations, for one) could fail with "Failed to fetch dynamically imported module". The app now reloads itself once to pick up the current files (never more than once in 30 seconds), and the error screen is only shown if that does not help.

## 30.12.5 (2026-11-26)

- **Home (SFW) has many more rows**, like a streaming app: new and featured movies and series, what is on Netflix, HBO Max, Disney+, Prime Video and Apple TV+, anime, rows for genres (Action, Comedy, Drama, Sci-Fi, Thriller, Horror and more) and the lists of the add-ons you added. Each row loads when you scroll to it, and leaves itself out when it has nothing (a removed add-on, no TMDB key).
- **A card's preview unfolds out of the card** when the pointer rests on it, the way dx.bi's does: the panel is revealed from the poster's own outline while the poster fades into its picture, the titles beside it glide aside, and a soft glow of the title's colours comes up around it. It shows the rating, genres and the story, and opens the page on a click.
- **The cast of a movie or show is clickable** (library and Discover pages): it opens a page with that person's movies and shows in your library, then their other work from TMDB, each opening its own page.
- **Missing episodes are shown in the show's page**: the episodes (and whole seasons) you do not have are listed with the catalogue's names, and each opens its episode page, where your add-ons offer streams for it.
- **An actor's page in SFW**: under Filmography the library's movies and series come first, then "More with …": the other movies and shows they are in (from TMDB, needs a TMDB key and a person linked to TMDB), each opening its Discover page. The Gallery tab is gone from SFW actors.

## 30.12.4 (2026-11-26)

- **Subtitles for torrent and web streams in SFW.** Stremio's own subtitle add-on (OpenSubtitles) is now built in, so the player's subtitle menu has subtitles before any add-on is installed. It is listed in Settings, Addons and can be removed and added back like the other built-in ones.

- Removed the **Integrations** page from Settings.
- In SFW mode no channel marked NSFW is listed any more, in the library or not. Before, only the NSFW channels that were in the library were hidden, so an NSFW channel outside the library (including one not sorted yet, which counts as NSFW) still showed by name on Transfers, Operations, the Photos and People pickers and in Settings, Telegram. The Rust front door answers the same. The channel list in Settings says how many are hidden; to sort or change them, switch to NSFW mode.
- Movie, series and Discover title pages no longer scroll as a page on wide windows: the page fits the window, and only a long overview or the episode and add-on panel scroll inside themselves.

## 30.12.3 (2026-11-26)

- Title pages show critics' scores and what critics said. Rotten Tomatoes and Metacritic scores sit beside the IMDb rating (on the Discover title page and on your library's movie and show pages), and a Reviews button next to Trailer opens the scores and the opening of the title's "Critical response" from Wikipedia, with a link to read the rest. They come from Wikidata and Wikipedia: no key and no account, only the title's IMDb number is sent (and only in SFW), the answer is kept for half a day, and a title they do not know simply has no marks or button.
- A title page takes its accent colour from its artwork (the buttons, links and marks on it), always moved to a shade white text reads on, and a black-and-white title keeps your accent. The picture is read on this computer. It is on unless you turn off "Match each title's colours" in Settings, Appearance (kept per computer); a picture from a host that does not allow reading is left alone.
- Torrent streams from add-ons (Torrentio and similar) now play, through Stremio's streaming server. Archive X still has no torrent code of its own: when Stremio (or its streaming service) is running on this PC or on your network, a torrent stream becomes a link on that server and plays like any other stream, with seeking. The address (usually http://127.0.0.1:11470) is in Settings, Addons, under "Streaming server for torrents", with a status line and "Check again"; it may only name this PC or your network, and it is only ever used for links built from a torrent's hash and file number. Without the server running, a torrent is listed with a note and a link to the setting. I could not test this against a real streaming server here, only against a stand-in that answers the same way; whether a video then plays also depends on its format (MKV and HEVC depend on the browser engine of the desktop window).
- Streams from add-ons read the seeds, size, source and "instant" (debrid-cached) marks that Torrentio writes in its text, so "Most seeds" and the size sorts work for it, rows show them, and there is an "Instant only" filter. How you sort and filter streams (order, language, source, HDR, instant) is remembered for the next title.
- The details panel beside the posters on Discover no longer has the "Open the page" and "Open in your library" buttons: the poster itself opens the title. The trailer button and the "Not in your library" mark stay.
- Switching between For you, Discover and Library in SFW is now seamless. The tab bar stays exactly where it is (it used to jump 111 px between For you and the other two, which also changed the page title and header layout), the three parts stay on the page once opened (coming back shows them at once, with no new requests, no blank moment and no replayed slide-in; each keeps its own scroll place), and once For you has loaded the other two are prepared out of sight so even the first switch is instant. While For you loads, the hero's place is kept so nothing shifts when it arrives. Measured in a browser: 0 px tab movement and 0 ms / 0 requests per switch after the first seconds, from 111 px and 300 to 550 ms before.
- Operations and Transfers list their jobs in one full-width column when there is only one job (it used to leave the right half empty), and in two columns when there are more. The same goes for the transfer processes on Operations.
- Add-ons can all be removed, including the three that come with the app (Cinemeta, Streaming Catalogs, Anime Catalogs). Removing one takes only its own lists out of Discover (Discover moves to a list that is still offered), and a removed one is listed under "Removed" in Settings, Addons with an "Add back" button. The whole-catalogue switch in Metadata still turns every built-in off.
- Add-ons exist in SFW mode only. In NSFW mode there is no Addons section in Settings, and the add-on endpoints refuse (or, for subtitles and details, find nothing), so no title or file name is sent to an add-on from NSFW.
- Each mode shows only its own tasks. Operations and Transfers (and the activity indicators, notifications and the Transfers lanes) list the tasks of the open mode; a task belongs to the mode of the channels or folders it works on, a task that names no channel shows in both, and a channel the library does not know counts as NSFW. The other mode's tasks are not listed: a line says how many are running or waiting in the other mode, and nothing about what they are.
- Transfers no longer rewrite the whole job state after every video while they prepare metadata. With 15,000 videos each save was about 50 ms on the event loop, roughly 6 minutes in all; the state is now saved every 200 videos or 5 seconds, and when the pass ends or is cancelled. (A stored caption cache was measured and left out: building a caption takes 0.05 ms per video.)
- The metadata match remembers what a video was searched with when it finds nothing. It already left such videos alone for 30 days; now a video whose filename, file hash or set of providers (or the visual-match choice) has changed since is asked about again at once, while an unchanged one is not. "Force" still asks about everything.
- Channel-to-channel transfers are faster and now report where their time goes. Each video's contact sheet is uploaded once (it used to be uploaded twice: as the video's cover and again as the picture), and videos are finished in groups: one read verifies a whole group, one call deletes the sources, one read confirms it (`delivery_batch_size` in the job, default 20, 1 = one at a time). With a simulated Telegram one video went from 12 calls to 9, and a group of 20 costs about 7 per video; real gains depend on Telegram's limits, so the log now prints a `Timing :` line every 10 videos and a final summary, including how long was spent waiting out flood limits. If Telegram refuses the shared upload, the transfer falls back to the old two-upload path by itself. A cancelled run leaves the posted copies and the untouched sources, and the next run finishes them. Also fixed: a resumed item whose copy already existed stopped with an internal error.

- The visual match (pHash) of the metadata scan is now optional. The Metadata tab of Transfers has a "Visual match (pHash)" check box with the processing stages (on by default, so results do not change; it applies with Metadata & Entity Data and is shown in the review before the run). Switched off, the scan matches by file name and file hash only, and skips computing the video's picture fingerprint, the provider lookups by fingerprint, the provider pictures it fetches for comparison, and the extra pass that runs after the snapshots are made. The choice is saved in the job (`visual_match`) and honoured by the metadata step, the pass after the snapshots and the local-media path; a job saved before this change behaves as before.

## 30.12.2 (2026-11-26)

- The database no longer only grows. A file never shrinks by itself: deleting a channel or rebuilding previews only marks space free inside it (measured: 837 MB on disk for 520 MB of content after half the previews were deleted). New databases are now made with incremental vacuum; an existing small one (under 256 MB) is switched at the start by one quick VACUUM (0.6 s for 80 MB, once); a larger one is switched from Settings → Storage → Database → Compact database, which also removes the space wasted inside half-empty pages (it shows the size, the unused space and the last times, asks first, needs free disk space about the size of the file, and refuses while a job runs).
- While the app is idle it gives unused space back in slices of 500 pages (each holds writing for under 100 ms), trims a write-ahead log above 128 MB, and refreshes the query statistics once a week (`PRAGMA optimize`, which also helps queries choose better plans). The first pass is two minutes after the start, then every six hours, and never while a job is running.
- Switching between SFW and NSFW is smoother and refreshes less: the screen no longer fills in piece by piece (five steps over a second when switching to NSFW, and the old mode's cards still showing for a moment after switching to SFW). The data of the mode you leave is remembered and the data you last saw in the mode you enter is shown at once, then refreshed behind it; a page with nothing remembered shows a skeleton, never the other mode's content; only what depends on the mode is fetched again (28 requests became 10), and what is remembered is forgotten when you sign out or after 10 minutes.
- Settings no longer walks the whole data folder every time it opens: the size is found by a direct directory scan (twice as fast, same totals) and kept; an old figure is shown at once and measured again in the background. With 250,000 files the storage request took 3.4 s and the page 4.4 s to settle; the first visit is now 1.2 s and the page 2.1 s, later visits are immediate.
- The studios list (0.42 s to 0.23 s for a first visit at 175,000 videos) and the performers list count through the base link tables, with the same answers in both content modes (checked on data with channels of both ratings).
- The channels list, asked by Videos, Transfers and Movies, reads its three big answers side by side (0.32-0.38 s to 0.18 s), through three long-lived workers, with the same answer.
- An open page no longer keeps the processor busy: the live connection asked for a fresh status four times a second, and each one counted every video's state in Python (0.18 s at 175,000 videos), about 40% of a core with the app idle. The three counts are now made by SQLite in one pass (reused for a few seconds), and the live connection sends the status only when something other than a heartbeat age changed (it sent 11 KB four times a second to an idle page; now once every 10 s). Idle processor with the page open: 41% to 2%.
- The one-time export of thumbnails and metadata after an upgrade works in batches (200 thumbnails and 500 videos at a time) and pauses briefly between them, instead of loading everything into memory at once: allocated memory during it stayed near 177 MB where it climbed to 1 GB at 175,000 videos, and real thumbnails are larger than the test ones.
- A database that kept the triggers of the stored Library list but lost its table (a partly copied or restored file) no longer stops the application starting: the table is made again and filled from the rule.
- Faster still on a large library: the stored list of Library videos now also keeps each video's channel, so a count or a page for some channels reads that index and not every video (a Library page 0.30 s to 0.08 s, a scanned channel of 15,000 videos 0.15 s to 0.013 s, a Library search 0.68 s to 0.11 s, with 175,000 videos of which 75,000 are prepared).
- The performers and studios lists are remembered until the data they are made from changes (videos, people, studios, channels, settings) and for at most 30 seconds; the first visit takes what it took (0.2 s and 0.4 s at 175,000 videos), the next ones about 10 ms.
- The test of live captions waits up to 90 s for its stand-in model, as a full test run on a busy machine can take longer than 30 s.
- The Library, channel, performer and studio pages no longer work out for every video, on every request, whether it is ready to be shown: the answer is kept in a table (`ax_library_ready`) that database triggers update when a video, its snapshots, thumbnail, representative image or split-file state changes. With 75,000 prepared videos the Library page went from 1.4 s to 0.24 s, a scanned channel from 0.15 s to 0.03 s, the performers list from 1.7 s to 0.3 s and a name search from 1.4 s to 0.26 s. The first start after the upgrade fills the table (about a second for 75,000 videos).
- A performer's page no longer takes time in proportion to the size of the whole library: it starts from the performer's own videos (0.59 s down to 0.025 s for a performer with 59 videos in a library of 175,000).
- A large library no longer makes the first start after an upgrade wait for the export of thumbnails and metadata to the user folders (15 s at 175,000 videos): it runs in the background, and the window opens at once.
- Fixed "the Archive X backend exited before it was ready ... database disk image is malformed": when the database file is damaged, the app now moves it aside into a `damaged-<time>` folder, creates a new database and copies back every row that can still be read, instead of refusing to start.
- Sixteen more handlers that read or write the database no longer do it on the web server's event loop, so a busy database cannot freeze the whole app (live updates, status) while they wait. Handlers that need the event loop to queue a job or a task keep that step on the loop.

- Fix: snapshots no longer fail "at random" on a busy PC. While one video's frames were being fetched from Telegram, other videos' bytes pushed them out of a shared 96 MB memory cache, and the frame failed with "Shared scan byte cache did not cover" (then "Fetched GOP range does not contain all requested samples"), which left the whole video without snapshots ("4 need Snapshots" in a Telegram transfer). The cause: once one video's cached bytes passed 96 MB (around frame 33 of 36 on a big video) the cache threw away the whole video, including what it had just stored, so the last frames failed. The cache now drops other videos first and only the oldest pieces of the same video, and a read also uses the pieces it just downloaded and fetches again only what is missing. A video still needs all 36 real frames; nothing is filled in from a neighbour.

- Fix: PyAV was reported "MISSING" on every installed copy (the log said "Archive X is already running with data folder ... Close the running Archive X first"), so every media job quietly used the slower FFmpeg path. The installed backend is one program with no separate Python; the PyAV health check and the isolated media worker were started with `-c` / `-m`, which it ignores, so each one started a second copy of the whole app that stopped at the one-instance lock.
